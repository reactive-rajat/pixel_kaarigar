UX Case Study · Design Systems

Rebuilding the design
foundation of ResumeHelp
from scratch

ResumeHelp is an online resume builder — part of Bold's product family. The product had scaled but the design never did. I owned the migration from an inconsistent, accessibility-broken theme to a proper design system that the whole team could actually trust.

Context

Why this project was needed

ResumeHelp had been around for a while. As the product grew — more pages, more markets, more people touching the design files — the original theme started falling apart. It was never really built as a "system." It was just a bunch of one-off decisions stacked on top of each other over the years.

01

Accessibility was broken

The primary green (#00C194) failed both WCAG AA and AAA contrast standards. For a product used by millions, this wasn't okay.

02

No shared design rules

Every designer made their own spacing, colour and layout decisions. There was no single source of truth anyone could point to.

03

Devs couldn't build with confidence

Without proper specs and a component library, developers had to keep asking designers "what font size is this?" or "what's the padding here?" for every single page.

04

Visually inconsistent product

Mixed icon styles, random dark sections, teal overlays on images, inconsistent typography — the product just didn't feel like one product anymore.

The Problem

6 things that were quietly broken

None of these were a "stop everything" kind of issue by themselves. But put them together and you get a product that feels patched together — and makes designing any new page without introducing more inconsistency almost impossible.

01

Failed colour contrast

White text on the primary green (#00C194) didn't pass WCAG standards. For a product used by regular people building their resumes, readability is everything.

02

Dark teal overlays on every hero

Every hero section had a dark overlay slapped on top of the photos. The images basically lost their purpose — you could barely see what was underneath.

03

No spacing or grid system

No defined margins, no grid columns, no padding rules. Every page was hand-eyeballed by whoever happened to design it.

04

Too few typography styles

Only 6 type styles for the whole product. That's just not enough when you have 15+ different page types with complex content hierarchies.

05

Chaotic icons — no consistency

Some pages had outlined icons, some had filled, some had two-colour icons from random packs. No one ever decided on a single icon family to use everywhere.

06

Random dark sections

Dark background sections were used randomly just to "visually separate" content. There was no logic — just habit.

Before

The old theme — what we were working with

Teal-heavy, overlays on everything, no defined spacing tokens, no structured type hierarchy. It was functional — but it didn't scale. And it definitely didn't meet accessibility standards.

Objective

Build a design system that actually works

The goal was simple to say but hard to execute — replace the old theme with a proper, scalable design system. Fix the accessibility issues. Give developers specs they can actually use. And make every page feel like it belongs to the same product.

🎯

Pass WCAG standards

Replace the failing #00C194 green with a new palette that passes AA and AAA contrast ratios.

🧱

One system, one source

A single Figma file with all tokens, components and specs. No more "which version is correct?"

🤝

Zero-friction dev handoff

Put the specs right on the canvas where developers can see them. No guesswork, no back-and-forth.

Process

How we got it done — step by step

I was working with one in-house designer and an external agency. My job was to lead the design system effort — brief the agency, validate everything before it reached developers, and make sure the final output actually made their life easier.

01

Stakeholder meetings

Had multiple alignment calls with PMs and product stakeholders to understand what the business actually needed from this redesign.

02

Briefed the agency

Put together detailed requirements for the external design agency — covering colour tokens, grid rules, typography needs and component expectations.

03

Continuous review

Closely monitored progress through Figma comments and calls. Flagged gaps, pushed for missing foundational pieces, and course-corrected early.

04

Built the foundations

Added structured grids, spacing tokens, a strict H1–H6 typography hierarchy, and unified all UI elements into a proper component library.

05

Dev-ready handoff

Put explicit front-facing specs right on the Figma canvas — so devs could see font sizes, spacing and colours without opening Dev Mode.

Foundations — Colours

A new colour palette that actually passes accessibility

The biggest pain point was the old green. #00C194 looked nice but white text on it was basically unreadable for people with any kind of visual impairment. The new palette was built with WCAG compliance as a hard requirement — not an afterthought.

The new structured colour palette — named tokens, WCAG-tested, ready for developers to pick up directly
Foundations — Typography

From 6 styles to a proper type hierarchy

The old system had only 6 type styles for the entire product. That's just not enough when you've got homepage heroes, blog articles, builder interfaces and legal pages all sharing the same design language. We built a full H1 through H6 scale, paragraph styles, caption sizes — everything documented with exact specs.

Complete typography scale — every heading level, paragraph style, and caption size defined with exact pixel values and weights
Foundations — Grid & Spacing

Structured grids and spacing tokens

Before this, every page was spaced by eye. One designer would use 40px between sections, another would use 60px, and nobody documented any of it. We introduced proper column grids and a defined vertical spacing system that everyone had to follow.

Column grid specifications — consistent layout framework across all pages
Vertical spacing tokens — defined values for section gaps, component margins, and content padding
Standardisation

One icon library to rule them all

The old product had icons from at least 3-4 different sources. Some were outlined, some filled, some were even custom two-colour icons that didn't match anything else on the page. We standardised the entire product under Font Awesome 5 (Solid) — one style, one weight, zero confusion.

Before

Mixed icon chaos

Outlined icons on one page, filled on another, custom two-colour icons on a third page. No pattern, no logic — just whatever each designer happened to pick.

After

Font Awesome 5 — Solid

One icon family, one weight (Solid), used everywhere. Developers could simply use the FA class names — no custom SVGs to manage, no confusion about which icon pack to use.

Component Library

Reusable components — built once, used everywhere

This was probably the most impactful part for the team. Instead of recreating buttons, navbars, breadcrumbs and forms from scratch on every new page, we built a global component library in Figma. Every state documented. Every variation covered. Designers could just drag and drop, developers could look at one place for specs.

Buttons — every colour variant, size, and state (default, hover, disabled) documented in one place
Breadcrumb navigation — consistent across all template pages
List styles — bullet, numbered, and feature list components
Logo specifications — proper usage rules for different contexts
Trust blade — standardised company logo strip used across landing pages
Circular colour buttons — used for resume template colour selection in the builder
Developer Handoff

Specs on the canvas — zero guesswork

This is something I'm genuinely proud of. Instead of just relying on Figma's Dev Mode (which, honestly, many developers don't love), I placed explicit specs directly on the canvas itself. Font sizes, line heights, spacing values — all visible right next to the actual components. Developers could look at the design and immediately know what to build.

Why front-facing specs matter

No back-and-forth

Devs don't need to hover over every element in Figma. The specs are right there — labelled, visible, clear.

Cross-product consistency

We mirrored the spec format from Bold's other product (ResumeGenius). Same formatting style = zero learning curve for devs switching projects.

Single source of truth

One Figma file. All tokens, all components, all specs. If it's not in this file, it doesn't exist in the product.

Impact

What changed after this

The whole thing took about 2-3 days of core execution to put together. But the impact on the team's workflow was immediate and lasting.

✅

WCAG compliant

The new colour palette passes both AA and AAA contrast standards. No more accessibility failures on primary buttons and CTAs.

⚡

Faster dev handoffs

Front-facing specs eliminated the constant "what's the font size here?" questions. Developers could build without waiting for design clarifications.

🎨

Premium, unified look

Standardised typography, icons, and components gave the product a cohesive visual identity. Every page finally felt like it belonged to the same product.

Reflection

Design systems aren't just about making things look pretty. They're about making sure a team of designers and developers — spread across time zones, working on different features — can all produce work that looks and feels like it came from one brain.

The ResumeHelp design system wasn't a massive 6-month project. It was an intense, focused effort to fix what was broken and build a foundation that could actually scale. The key was being hands-on with both the agency and the dev team — not just throwing a Figma file over the fence and hoping for the best.

The 15-page template migration that followed (covered separately) was only possible because this foundation existed. Without it, every new page would have just added more inconsistency to the pile.
